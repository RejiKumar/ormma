One line per non-obvious decision. Tags: [DECIDED] final; [PROPOSED Sn] default to resolve in stage n; [SPEC-CONFLICT] needs a spec edit when approved.

- #1 [DECIDED 2026-10-16, reconcile-proposed-decisions, specs call-flow and consent updated] Add call type "consent", allowed while consent.status is "pending"; it plays only the consent script and writes no health data. All other calls still require "granted", and the parent must still be `active`. Why: a first consent call is the only way to get voice or DTMF consent (consent spec, granting method 1), so one call type must be allowed while pending; limiting it to the consent script with no health data keeps "no calls or health logging until granted" true for everything else.
- #2 [DECIDED 2026-10-16, specs 01, 02, 03 updated] Family may change `missed` to `taken` (resolvedBy "family"). `missedAt` is kept, `missed` stays terminal for all server transitions, and no alert is re-sent or retracted.
- #3 [DECIDED 2026-10-16, reconcile-proposed-decisions, spec data-model updated] `prescriptions.extracted` uses the `prescription-reading` schema (frequencyText, illegible, nullable doseText/times, overallConfidence). Why: that schema is what the model returns and what the review screen edits; another stored shape would need a lossy mapping, and nullable fields let missing values stay missing instead of being filled in (medical-safety).
- #4 [DECIDED 2026-10-16, reconcile-proposed-decisions, specs data-model and data-protection updated] Transcripts are stored only when needsReview, under `transcripts/review/`, deleted when the review is resolved or after 30 days, whichever comes first. Why: transcripts are only needed for human review, so keeping only those and deleting them on resolution minimises data (data-protection); 30 days bounds unresolved ones.
- #5 [DECIDED 2026-10-16, reconcile-proposed-decisions, spec access-control updated, Rules test 15 added] Parent creation is callable-only: the function writes the parent and its owner member in one batch. Clients cannot create parents directly. Why: one batch avoids a parent without an owner or a client granting itself a role, and rules cannot make two writes atomic.
- #6 [DECIDED 2026-10-16, reconcile-proposed-decisions, spec data-model updated] `members/{uid}` carries `displayName` (copied by the function at create/invite acceptance); `users/{uid}` stays self-only. Why: the family app must show who else has access without reading other users' `users/{uid}` documents, which stay self-only for privacy.
- #7 [DECIDED 2026-10-16, specs 01, 02, 05 updated] `consent.revokedAt`; after revocation, rules hide healthLogs/alerts (createdAt) and doseEvents (scheduledFor) dated at or after revokedAt from non-owners; older data stays visible. Queries must repeat the date filter. Re-grant is decided in #7a, repeated revocation in #7b.
- #7a [DECIDED 2026-10-16, specs 01, 02, 05 updated] Re-grant keeps `revokedAt` and adds `regrantedAt`; non-owners read data dated before revokedAt or at/after regrantedAt; data in between stays hidden from non-owners; owners see everything.
- #7b [DECIDED 2026-10-16, specs 01, 02, 05 updated] v1 limitation: one revoke/re-grant cycle only. A second revocation keeps the FIRST `revokedAt` and clears `regrantedAt`, so non-owners see only data from before the first revocation. History between a re-grant and a later revocation is hidden from non-owners on purpose (fail closed); overwriting `revokedAt` would expose the first gap. Revisit with a `consentGaps[]` array if repeated revocation matters.
